# GLEIF CSV field map

Checked: 11 November 2026.

This file lists the GLEIF CSV files and exact column names we use. It explains what each field is used for. GLEIF-field-map.csv has one row for each source column, with its source CSV, usage and purpose. It also identifies fields we save without using and fields we do not save.

The source files are from the saved GLEIF publication dated 15 October 2026, 08:00 UTC. These usage notes describe the local version reviewed on 11 November 2026. This does not confirm which version is running on the remote machine.

## How to read the usage labels

- Identifier and checks: identifies records, supports comparisons and provides review context.
- Checks and context: used in checks and provided as review context.
- Related-record lookup: used to find related records.
- Context only: provided to the reviewer or AI as background. It does not decide a match on its own.
- Saved only: saved, but not currently used in the review.
- Not saved: present in the source CSV, but not saved.

Evidence is bounded and depends on which entities are reviewed. Inclusion in the catalog does not mean that every row is sent to AI. Candidate fields remain unconfirmed until identity is checked.

### Repeated names, events and successors

n means each number from 1 to 5. The companion CSV expands every name below into its exact numbered source columns.

- Entity.OtherEntityNames.OtherEntityName.n: alternative name, used for name search and comparison.
- Entity.OtherEntityNames.OtherEntityName.n.type: describes the alternative name.
- Entity.TransliteratedOtherEntityNames.TransliteratedOtherEntityName.n: transliterated name, used for the same name search and comparison.
- Entity.TransliteratedOtherEntityNames.TransliteratedOtherEntityName.n.type: describes the transliterated name.
- Entity.SuccessorEntity.n.SuccessorLEI: links an entity to an explicit successor and lets us retrieve its record.
- Entity.SuccessorEntity.n.SuccessorEntityName: successor name, used as context.

The following columns all start with Entity.LegalEntityEvents.LegalEntityEvent.n.:

| CSV column suffix | How we use it |
| --- | --- |
| LegalEntityEventType | Checks the type of event, including a merger or acquisition. |
| LegalEntityEventEffectiveDate | Checks when the event took effect. |
| event_status | Checks whether the event is completed. |
| LegalEntityEventRecordedDate | Shows when the event was recorded; context only. |
| ValidationDocuments | Provides validation context. |

For example, Entity.LegalEntityEvents.LegalEntityEvent.1.LegalEntityEventType is the exact column for the first event type. The companion CSV lists every numbered column separately.

An alternative name needs a non-empty name. An event needs a non-empty event type. A successor needs an LEI or a name. Empty items are skipped.

## 2. Relationships: rr

Source CSV: 20261015-0800-gleif-goldencopy-rr-golden-copy.csv

We save all 54 source columns. The following five fields identify and classify each relationship:

| Exact CSV field | Purpose |
| --- | --- |
| Relationship.StartNode.NodeID | Starting entity; used to retrieve outgoing relationships. |
| Relationship.EndNode.NodeID | Other endpoint; used for direct links, shared ultimate parents and related-entity lookups. |
| Relationship.RelationshipType | Distinguishes consolidation from branch/fund relationships; selects direct and ultimate consolidation rules. |
| Relationship.RelationshipStatus | ACTIVE is required by the current-conclusion rule. |
| Registration.RegistrationStatus | PUBLISHED is required by the current-conclusion rule. |

Interpret Relationship.StartNode.NodeID and Relationship.EndNode.NodeID together with Relationship.RelationshipType. For a fund or branch relationship, the end node is not automatically an owner.

We also use these CSV fields for dates and validation context:
- Relationship.Period.n.startDate
- Relationship.Period.n.endDate
- Relationship.Period.n.periodType
- Registration.LastUpdateDate
- Registration.NextRenewalDate
- Registration.ValidationSources
- Registration.ValidationDocuments

Here n is 1 to 5. The period type, relationship-period bounds, accounting-period end and next renewal date feed the eligibility checks. Update date and validation values are context.

Retained but not selected into current relationship evidence: Relationship.StartNode.NodeIDType, Relationship.EndNode.NodeIDType, all Relationship.Qualifiers.*, all Relationship.Quantifiers.*, Registration.InitialRegistrationDate, Registration.ManagingLOU and Registration.ValidationReference. Storage of a quantifier does not mean the application uses it as an ownership percentage.

## 3. Reporting exceptions: repex

Source CSV: 20261015-0800-gleif-goldencopy-repex-golden-copy.csv

| Exact CSV field | Purpose |
| --- | --- |
| LEI | Entity lookup |
| Exception.Category | Parent-reporting category |
| Exception.Reason.1 through Exception.Reason.5 | Non-empty reasons, in source order |

Exception.Reference.1 through Exception.Reference.5 are not retained. Exceptions are included in the review evidence and candidate context. They do not prove that two entities are unrelated.

## 4. What does not come from these CSVs?

- Simplified names used for searching are derived from Entity.LegalName or an alternative name.
- Match status, similarity scores, comparison messages and whether a relationship supports a current conclusion are calculated by our application.
- The source download URL, file checksum and publication timestamp come from the saved download manifest. They are not company fields in these CSVs.
- Import time and completion status are recorded locally.
- Internal company IDs, CRDS IDs, Booking Codes and Settlement Routing IDs are internal inputs. They are not supplied by these three GLEIF CSVs.

## 5. Which fields affect a current conclusion?

- A supplied LEI or a unique authority-plus-registry-ID match can confirm identity. A supplied jurisdiction is checked when present. Name search alone returns candidates.
- Same confirmed LEI supports the same-entity check.
- Direct/ultimate consolidation and shared ultimate-parent checks use both endpoint IDs and the relationship type.
- Current consolidation eligibility checks ACTIVE relationship status, PUBLISHED relationship registration, next renewal, and the period fields. It also checks entity ACTIVE/ISSUED status and entity renewal.
- The catalog must be no more than 31 days old and not future-dated. A qualifying accounting period must end no more than 730 days before the catalog date. These are application thresholds, not GLEIF field definitions.
- Explicit successor evidence uses SuccessorLEI. The merger interpretation also requires a COMPLETED MERGERS_AND_ACQUISITIONS event with an effective date at or before the catalog date.
- Background information alone does not prove a relationship.

## 6. How to find a field in the source CSV

1. Open GLEIF-field-map.csv.
2. Read source_csv to identify the GLEIF file.
3. Read source_column for the exact header in that file.
4. Read usage and purpose to see how we use it.
5. retained=YES means we save the field. It does not necessarily mean we use it in a decision. Saved only identifies fields that we save without using in the current review.

Examples:
- 20261015-0800-gleif-goldencopy-lei2-golden-copy.csv -> Entity.LegalName -> company name search and comparison.
- 20261015-0800-gleif-goldencopy-rr-golden-copy.csv -> Relationship.EndNode.NodeID -> the other entity in the relationship; interpret it with Relationship.RelationshipType.
- 20261015-0800-gleif-goldencopy-repex-golden-copy.csv -> Exception.Reason.1 -> a reason parent information was not reported.

All 404 documented column names were checked against the headers in the three saved source CSVs. The usage notes distinguish fields we use, fields we only save, and fields we do not save.
